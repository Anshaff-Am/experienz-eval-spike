Track A — LibreChat → LiteLLM → Bedrock (Langfuse)

A1 — session_id in Langfuse

STOPPED

Langfuse requires a session_id on each trace to group a conversation. LibreChat's conversation ID is available in the app layer but is stripped from the request before it reaches the LLM call — the field never enters LiteLLM's callback payload, so Langfuse never receives it.

Stop condition hit Gate A1 requires session_id to reach Langfuse on 100% of 20 test messages across 3 conversations. It reaches 0%. This is a structural gap in LibreChat, not a configuration issue.

What it would take to fix: fork LibreChat, propagate conversationId through the request chain to the LiteLLM handler, and surface it as a custom metadata field in Langfuse's callback. Estimated effort: 3–5 days (LibreChat is a large codebase; the hook point is deep in the conversation handler).

No gates beyond A1 were built. Per the spike brief, gates are sequential and load-bearing. A2–A5 all assume A1 holds.

Track B — Analytics Engine on AgentCore

B1 — Live scoring via AgentCore Evaluations

PASS

Five real agent sessions scored against three built-in AgentCore evaluators: Builtin.GoalSuccessRate (SESSION scope), Builtin.InstructionFollowing (TRACE scope), and Builtin.Helpfulness (TRACE scope). 15 evaluation API calls total, all returning numeric scores.

The key challenge: the analytics agent does not emit native OTel spans. Spans were constructed from CloudWatch logs — no agent code changed. Span construction method:

  • sessionId — pulled from the JSON structured app log field
  • traceId — requestId with dashes stripped → 32-char hex
  • Tool sequence — plaintext agent log, regex agent tool=(\w+) ok=
  • Timestamps — from CloudWatch log stream metadata

OTel span format that the API accepts (discovered through trial-and-error — not documented):

sessionSpans: [{
  sessionId: "7caf7172-3ba9-...",
  spans: [{
    traceId: "7caf71723ba9...",   // 32-char hex, no dashes
    spanId: "a1b2c3d4e5f60001",
    parentSpanId: null,
    name: "get_stage",
    kind: "INTERNAL",            // string, not enum
    status: { code: "OK" },      // string, not int
    startTimeUnixNano: "...",
    endTimeUnixNano: "...",
    output: { value: "{...}" },  // required for tool spans
    scope: { name: "analytics-agent", version: "1.0" }
  }]
}]

Why session 5 scoring 0.0 is a good result Session 03744d72 ran preview_cube only — it never completed the pipeline task. GoalSuccessRate = 0.0 is the correct verdict. This proves the evaluator is reading task outcome, not just checking that spans arrived.

Caveat: output.value for tool spans was inferred (realistic JSON), not captured from real CloudWatch output fields. The scoring engine receives it — the scores are real — but the output content is synthetic for this gate.

B3 — In-order trajectory matching

PASS

Expected tools must appear as a subsequence of actual tools — extra steps between required steps are tolerated; a missing required step or reordering fails. Pass bar: ≥80% of runs match. Stop floor: <50% → fall back to B2 artifact checks only.

6 real production sessions used (target was 12; Sept-04 CloudWatch streams were infra-only with no agent runs; Sept-09 sessions were warmup/smoke tests).

RunTask typeExpected toolsActual toolsResult
G01 rerun get_stage → rerun_stage get_stage → rerun_stage MATCH ✓
G02 schema-preview preview_cube preview_cube MATCH ✓
G03 status-check get_run get_run MATCH ✓
G04 inspect-and-rerun get_stage → rerun_stage get_stage → preview_cube → rerun_stage MATCH ✓
G05 rerun get_stage → rerun_stage get_stage → rerun_stage MATCH ✓
G06 list-runs list_runs list_runs MATCH ✓
G04 — why this is the proof run G04's expected trajectory is get_stage → rerun_stage. The agent actually ran get_stage → preview_cube → rerun_stage — it inserted an inspection step between the required ones. The in-order matcher correctly accepts this: preview_cube is a tolerated extra step, not a failure. If the matcher were doing exact-sequence matching, G04 would fail. It doesn't.

Result: 6/6 = 100% (bar: ≥80%). Gate passes.

Caveat: the golden set was constructed from the same 6 sessions used as actual. This proves the matcher logic is correct — it is not yet a regression test against future runs. When new production sessions accumulate, add them to golden-sets/b3-trajectories.json with independently verified expected trajectories.

Three Decisions — from the spike brief

The spike brief is explicit: three platform decisions are the output. Evidence for each is below.

1 — Which platform runs evaluation for the front-facing chat?

Evidence: Langfuse on hosted tier is wired into LiteLLM's native callback and traces arrive, but session_id (LibreChat conversation ID) is never passed — the field is stripped before the LLM call. A1 failed its 100% bar on day 1. Cost to fix: LibreChat fork + LiteLLM patch, ~3–5 days.

CONTINUE
Fork LibreChat, absorb 3–5 days, then resume Track A at A2. Langfuse otherwise fits well — hosted tier is free at spike volume, LiteLLM callback is native, A4 diff loop is its strongest feature.
STOP
Stop Track A. Report Langfuse integration cost as 3–5 days before any eval signal. Consider promptfoo + own harness for A3/A4 — no session_id dependency, cheaper to wire, harness stays ours.

2 — Is AgentCore Evaluations sufficient on its own for the analyst agent?

Evidence: B1–B3 passed. Built-in evaluators return real scores against CloudWatch-constructed spans — no agent re-instrumentation. B2 deterministic checks are the strongest signal (schema compile, DQ hard gates, ±0.5pp reconciliation). B3 trajectory matching at 100% on 6 sessions. The native advantage (close to free, same platform as the agent) appears real.

Open item: B4 live CI proof blocked by codebuild:StartBuild = implicitDeny. Local PoC (broken schema → exit 1, good schema → exit 0) can be run; admin needs to grant the permission for a live build trigger to close the gate fully.

Recommendation: yes, sufficient — with the caveat that B3's golden set needs to grow beyond 6 sessions as production traffic accumulates. The deterministic B2 checks are the load-bearing layer; trajectory matching is additive.

3 — Do the two tracks stay separate or converge onto one stack?

Evidence from this spike: Track A stopped at A1 so no cross-platform comparison was completed. Track B is running on AgentCore natively. Putting Track A onto AgentCore would require the same LibreChat/LiteLLM plumbing work regardless of eval platform.

Spike brief guidance: unify only if it costs ≤2 days — otherwise note it as an option. Based on what we found: unification is not the current bottleneck; the bottleneck is Track A's session_id gap. Recommendation: keep separate until Track A's platform is settled; revisit convergence after A1–A3 pass.
